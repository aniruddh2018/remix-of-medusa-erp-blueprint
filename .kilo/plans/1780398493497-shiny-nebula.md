# Plan: Real Accounting Ledger Integration

## Goal
Make ledgers behave like a real double-entry accounting tool:
1. Every sale, purchase, and payment creates proper accounting entries (journal vouchers).
2. Ledger balances reflect actual financial transactions (not in-memory ad-hoc sums).
3. Customers / Suppliers are unified with ledgers (read from `ledgers_with_roles`, balances synced).
4. The Accounts page shows real ledger balances and transaction history from the DB.

---

## Context

### Existing (from graphify + code read)
- **Unified ledger schema** exists: `ledger_groups`, `ledgers`, `ledger_roles`, `ledger_balances`, `ledgers_with_roles` view.
- **Bridge service** (`ledgerBridge.ts`): one-way sync `customers`/`suppliers` → `ledgers` on create/update.
- **No journal/voucher system** exists. `ledger_balances.current_balance` = `opening_balance` only (placeholder trigger).
- **Accounts.tsx** computes balances in-memory from `sales_orders` + `purchase_orders` + `payments`.
- **Sales.tsx / CounterSales.tsx** insert into `sales_orders` + `sales_order_items` + `payments` but never touch ledgers.
- **RecordPaymentDialog.tsx** inserts into `payments` only, never into ledgers.
- **Customers.tsx / Suppliers.tsx** still read from separate `customers`/`suppliers` tables (not from `ledgers_with_roles`).

## Phase 1 — Journal Voucher (Double-Entry) Schema

### 1.1 New Tables
Create a new Supabase migration:
- **`journal_vouchers`**
  - `id`, `company_id`, `date`, `reference_type` (enum: sales_order, purchase_order, payment, adjustment), `reference_id`, `reference_number`, `narration`, `total_amount`, `created_by`, `created_at`.
- **`journal_voucher_lines`**
  - `id`, `voucher_id`, `ledger_id`, `company_id`, `debit_amount`, `credit_amount`, `narration`.
- Indexes: `(company_id, date)`, `(voucher_id)`, `(ledger_id, date)`, `(reference_type, reference_id)`.
- RLS policies mirroring existing ledger policies.

### 1.2 Auto-Post Triggers / Functions
Create PostgreSQL functions + triggers:
- **`post_sale_voucher()`** — trigger AFTER INSERT on `sales_orders`:
  - **Cash/UPI/Card sale**: Dr Cash/Bank ledger → Cr Sales Income ledger.
  - **Credit sale**: Dr Customer Ledger (resolved by name) → Cr Sales Income ledger.
  - Also insert payment voucher if `payment_status = 'paid'` and `amount_paid > 0`.
- **`post_purchase_voucher()`** — trigger AFTER INSERT on `purchase_orders`:
  - Dr Purchase Expense ledger → Cr Supplier Ledger (resolved by `supplier_id` → `suppliers.name` → `ledgers.name`).
- **`post_payment_voucher()`** — trigger AFTER INSERT on `payments`:
  - Payment received: Dr Cash/Bank ledger → Cr Customer Ledger.
  - Payment made: Dr Supplier Ledger → Cr Cash/Bank ledger.
- **`delete_cascade_voucher()`** — trigger AFTER DELETE on `sales_orders`/`purchase_orders`/`payments` to delete linked vouchers.

> **Decision needed**: Triggers run as service-role (bypass RLS) so they can resolve ledgers by name. Alternative: edge function or app-layer posting. **Recommendation**: DB triggers for reliability (sales happen even if frontend misses it).

### 1.3 Resolve Ledger IDs by Name
Since `sales_orders.customer_name` is TEXT and `payments.party_name` is TEXT, the trigger must look up `ledgers.name` (case-insensitive, within company). If no match, create a fallback ledger under "Sundry Debtors" / "Sundry Creditors" automatically.

## Phase 2 — Ledger Balances from Vouchers

### 2.1 Replace Placeholder Trigger
- Drop `trg_ledgers_balance` + `update_ledger_current_balance()`.
- Create **`recalculate_ledger_balance()`** function:
  - Sums all `journal_voucher_lines` for a `ledger_id` within the financial year.
  - Updates `ledger_balances.current_balance`, `total_debit`, `total_credit`, `closing_balance`.
- Create trigger AFTER INSERT/UPDATE/DELETE on `journal_voucher_lines` that calls `recalculate_ledger_balance()` for affected ledgers.

### 2.2 Backfill Existing Data
- One-time migration script that iterates existing `sales_orders`, `purchase_orders`, `payments` and creates corresponding `journal_vouchers` + `journal_voucher_lines`.
- After backfill, `ledger_balances` will have real numbers.

## Phase 3 — Frontend: Real Ledger Balances & History

### 3.1 Accounts.tsx Refactor
- Remove in-memory `unifiedLedger` computation from `sales_orders` + `purchase_orders` + `payments`.
- Query `ledgers_with_roles` view (or a new `ledger_balances_with_names` RPC/view) for real balances.
- Transaction detail expansion should query `journal_voucher_lines` joined to `journal_vouchers` instead of ad-hoc order arrays.
- Keep CSV/PDF exports but source data from real ledger entries.

### 3.2 New DB View / RPC for Ledger Transactions
- Create view `ledger_transaction_history(ledger_id, date, ref_type, ref_number, narration, debit, credit, running_balance)`.
- Or RPC `get_ledger_transactions(ledger_id, year, limit, offset)`.

### 3.3 Customers.tsx & Suppliers.tsx
- Replace direct `customers` / `suppliers` table queries with queries against `ledgers_with_roles` filtered by role.
- Show `currentBalance` from `ledger_balances` instead of ad-hoc outstanding calculation.
- Edit dialog should update the **ledger** (via `ledgerService.updateLedger`), and the bridge should sync back to `customers`/`suppliers` (bi-directional).
- Add a "Ledger Transactions" tab showing real double-entry history.

### 3.4 Sales.tsx / CounterSales.tsx — Link to Ledgers
- When creating a sale, ensure `customer_name` maps to an existing ledger.
- If the customer is selected from `customers` table, auto-sync to ledger first (or ensure they already share a ledger).
- Long-term: add `ledger_id` to `sales_orders` (DB migration) so triggers don't need fuzzy name matching.

---

## Phase 4 — Bi-Directional Sync & Data Integrity

### 4.1 ledgerBridge.ts Enhancements
- `syncCustomerToLedger()` already exists (customer → ledger).
- Add **`syncLedgerToCustomer()`**: when a ledger with `customer` role is created/updated, upsert into `customers` table.
- Add **`syncLedgerToSupplier()``: when a ledger with `supplier` role is created/updated, upsert into `suppliers` table.
- Add DB trigger on `ledgers` INSERT/UPDATE that auto-calls these (or do it in app layer with `ledgerService`).

### 4.2 Deletion Policy
- Deleting a customer/supplier should NOT delete the ledger (it holds accounting history).
- Instead: deactivate (`is_active = false`) the corresponding ledger role, or mark ledger as inactive.
- UI should warn: "This party has ledger transactions. Deactivating will hide them from lists but preserve history."

---

## Phase 5 — Chart of Accounts (LedgerManagement.tsx) Polish

### 5.1 Show Real Balances
- `LedgerManagement.tsx` already queries `ledgers`. Update to show `currentBalance` from `ledger_balances` (current financial year).

### 5.2 Trial Balance Integrity
- `trial_balance()` RPC already groups by `ledger_group`. After Phase 2, it will produce correct numbers because `ledger_balances` is populated from real vouchers.

### 5.3 Audit Trail
- Already exists (`ledger_audit_log`). Ensure it captures voucher-level actions too (optional).

## Open Questions for User

1. **Cash/Bank ledgers**: Do you already have Cash-in-Hand and specific Bank Account ledgers seeded per company? If not, the auto-post triggers need to know which ledger to debit/credit for cash sales/payments.

2. **Sales Income / Purchase Expense ledgers**: Do you want auto-created generic ledgers (e.g., "Sales Account", "Purchase Account") under Income / Expenses groups, or do you want to map to existing product-based accounts?

3. **Scope of backfill**: Should we backfill all historical sales/purchases/payments into journal vouchers so past balances are correct, or only from now forward?

4. **Multi-company**: Are you running multiple companies? The triggers need `company_id` isolation — already handled by RLS but triggers run as definer.

## Success Criteria

- [ ] Creating a cash sale auto-creates a journal voucher: Dr Cash → Cr Sales.
- [ ] Creating a credit sale auto-creates: Dr Customer Ledger → Cr Sales.
- [ ] Recording a payment auto-creates: Dr Cash/Bank → Cr Customer (or Dr Supplier → Cr Cash/Bank).
- [ ] `ledger_balances.current_balance` updates automatically after every transaction.
- [ ] Accounts page shows real balances from `ledger_balances`, not in-memory sums.
- [ ] Customers page shows balances from `ledger_balances`.
- [ ] Suppliers page shows balances from `ledger_balances`.
- [ ] Trial Balance report totals match (debit = credit ± rounding).
- [ ] Deleting a sale reverses its voucher (cascade delete).
